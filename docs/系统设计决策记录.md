## 一、已知技术约束

### 1.1 FAISS 不支持中文路径

**约束**: FAISS C++ 底层 `fopen()` 无法正确处理含中文字符的路径，`read_index()` 和 `write_index()` 直接报错。

**解决方案**: 加载/保存时先复制到 `tempfile.TemporaryDirectory()`（纯 ASCII 路径），操作完成后再移回目标路径。

**涉及模块**: `src/ingestion.py`, `src/retrieval.py`

```python
# 加载模式
with tempfile.TemporaryDirectory() as tmp_dir:
    tmp_faiss = os.path.join(tmp_dir, "index.faiss")
    shutil.copy2(str(source_path), tmp_faiss)
    index = faiss.read_index(tmp_faiss)
```

### 1.2 DashScope Embedding 2048 token 输入上限

**约束**: `text-embedding-v3` 单次输入上限 2048 tokens（cl100k_base 编码）。超过上限直接 API 报错。

**解决方案**: 调用 Embedding 前使用 tiktoken 截断文本到 `MAX_INPUT_TOKENS=2048`。

**涉及模块**: `src/retrieval.py` (`truncate_text_to_tokens`), `src/ingestion.py`

### 1.3 MinerU 单次解析页面数上限约 200 页

**约束**: MinerU API 单次请求支持约 200 页 PDF，超大型年报（300+ 页）会失败。

**解决方案**: 分页解析，每批 150 页，结果合并。

**涉及模块**: `src/pdf_mineru.py`

### 1.4 Windows 系统环境变量读取

**约束**: Windows PowerShell `.NET` 方式设置的系统环境变量不会立即注入当前进程，`os.getenv()` 读不到。

**解决方案**: 增加 `_read_windows_env_var()` 函数，通过 PowerShell 调用 `[System.Environment]::GetEnvironmentVariable()` 读取 User 和 Machine 作用域的环境变量。API Key 获取优先级：进程环境变量 → Windows 注册表 → `.env` 文件。

**涉及模块**: `src/utils.py` (公共函数，4 个模块共用)

### 1.5 DashScope API 超时控制

**约束**: 网络波动可能导致 API 请求无限挂起。

**已实施的超时配置**:

| API 类型 | 超时(秒) | 失败策略 |
|---------|---------|---------|
| LLM 生成 (qwen-max/plus) | 60 | 抛出异常，上层处理 |
| Embedding (text-embedding-v3) | 30 | 指数退避重试，最多 3 次 |
| gte-rerank-v2 重排 | 15 | 回退到 hybrid 分数排序 |

**涉及模块**: `src/retrieval.py`, `src/query_processor.py`

### 1.6 Markdown 表格文本对 Embedding 不友好

**约束**: Markdown 表格的排版符号（`|`, `-`, `:`）被 Embedding 模型视为噪声，降低检索精度。

**解决方案**: `preprocess_table_text()` 函数，Embedding 前自动检测并移除表格排版符号，将竖线替换为空格。

**涉及模块**: `src/retrieval.py`

## 二、架构决策

### 2.1 按公司分库，非统一索引

**决策**: 4 家公司（中芯国际、中国移动、中国联通、中国电信）各自维护独立的 FAISS + BM25 索引，通过 `company_registry.json` 注册。

**理由**:
- 用户查询通常针对特定公司，单库检索效率更高
- 跨公司对比时并行检索各公司索引，结果按公司公平分配
- 新增公司时不需重建全部索引

**检索流程**:
```
用户指定公司 → 单库检索 → 重排
用户未指定   → 所有公司并行检索 → 合并 → 重排
```

### 2.2 Small-to-Big 文本分块策略

**决策**: 子块 150 tokens 用于 Embedding 检索，父块 500 tokens 用于 LLM 上下文。

| 层级 | Token 数 | 用途 |
|------|---------|------|
| 子块 (Child) | ~150 | FAISS Embedding 检索 |
| 父块 (Parent) | ~500 | LLM 生成上下文 |

**理由**: 小块检索精度高但上下文不足，大块上下文丰富但检索不准。Small-to-Big 兼顾两者。

### 2.3 BM25 + 向量混合检索，意图驱动动态权重

**决策**: 使用 `rank_bm25` + `jieba` 分词进行关键词检索，FAISS 进行向量语义检索，加权融合后送入重排。

**默认权重**: BM25=0.5, 向量=0.5

**意图驱动权重调整**:

| 意图 | BM25 权重 | 向量权重 | 理由 |
|------|----------|---------|------|
| financial_data | 0.6 | 0.4 | 精确数值匹配优先 |
| comparison | 0.5 | 0.5 | 均衡 |
| business_analysis | 0.4 | 0.6 | 语义理解优先 |
| trend | 0.3 | 0.7 | 语义理解优先 |

### 2.4 gte-rerank-v2 批量重排

**决策**: 使用 DashScope `gte-rerank-v2` 专用重排模型进行批量评分，替代逐条 LLM 调用。

**效果**: 重排耗时从 30-60s 降至 ~2s，评分一致性显著提升。超时时自动回退到 hybrid 分数排序。

### 2.5 查询处理管线

**决策**: 所有查询先经过 `QueryProcessor`（意图识别 + 改写 + 域外拦截），再进入检索管线。

**处理流程**:
```
原始查询 → 意图识别 (6分类) → 域外拦截 → 查询改写 → 检索
```

**意图分类**: financial_data / business_analysis / comparison / trend / general / out_of_domain

**置信度阈值**: 0.4，低于此值标记为低置信度需人工确认

### 2.6 多公司对比四层保底

**决策**: 跨公司对比查询时，确保每家公司都有数据代表。

**四层防线**:
1. **公平分配**: 每家公司至少 5 个名额进入重排候选
2. **替换策略**: 缺失的公司替换过度代表公司的最低分结果
3. **保底重新检索**: 前两层失效时用聚焦查询重新检索
4. **营收数据保底补充**: 重排后某家公司结果仍不含关键财务数字时，从候选池补充含数据文档块

## 三、数据管道（Agent 项目完全继承，不变）

```
PDF 文件
  → src/pdf_mineru.py (MinerU API, 分页解析)
  → Markdown 文件
  → src/text_splitter.py (Small-to-Big 分块, tiktoken cl100k_base)
  → chunked_reports/*.json
  → src/ingestion.py (FAISS 索引 + BM25 索引 + 元数据 + 父块文本)
  → vector_dbs/ (按公司分库)
```

**管道输入**: `pdf_reports/*.pdf`
**管道输出**: `data/stock_data/databases/vector_dbs/{公司名}/`
**中间产物**: `chunked_reports/*.json`, `debug_data/03_reports_markdown/`

## 六、BM25 查询扩展机制

**词典文件**: `config/bm25_expansions.json` (18 个术语)

**扩展逻辑**: 用户查询中的关键词自动替换为扩展词集合，提升关键词检索召回率。按 key 长度降序匹配，防止短 key 覆盖长 key。

示例: "营收" → "营收 营业收入 收入"

**jieba 自定义词典**: `config/financial_dict.txt` (27 个财经术语)，确保 jieba 正确分词财经专有名词。
