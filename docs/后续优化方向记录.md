## OPT-01: 联网检索工具（可选增强）

### 背景

当前 5 个工具（retrieve/calculator/compare/chart/verify）全部基于离线年报索引。当用户询问"当前股价""行业政策""同行竞品数据"时，离线索引无法覆盖。

### 设计要点

1. **一键开关（toggle）**：界面侧边栏 `st.toggle("联网检索")`，默认关闭。参考现有"Agent 推理模式"开关模式
2. **按需触发**：Agent 先走本地索引，检索结果为空或置信度过低时才发起联网请求
3. **结果标注**：联网数据在回答中标注来源 URL，与年报原文引用区分
4. **注册制接入**：不注册 = LLM 完全不知道有联网能力，零侵入

### 实现路径

```
src/tools/web_search_tool.py  ← 新增工具类
app_streamlit.py              ← 侧边栏 toggle + 条件注册
config/agent_config.json      ← optional_tools 配置节
```

### 讨论记录

- 2026-06-23: 确定作为可选增强而非第 6 个默认工具，保持"所有结论有出处"的可靠性基线
- 2026-06-23: 建议核心版本 14 篇文章发完后再排期实现，届时可作为独立文章素材

## OPT-05: 推理过程实时流式输出

### 背景

当前 `agent_core.py` 的 `run()` 是同步方法，全部步数完成后才返回 `AgentResult`。Streamlit 界面用 `st.status` 显示静态的"推理中..."，用户盯着 spinner 等待 5~30 秒后突然看到答案，中间过程完全黑箱。

改为流式输出后，用户逐条看到 Thought → Action → Observation，感知等待时间大幅缩短，且能看到 Agent "正在想什么"，信任感直接提升。

### 设计要点

1. **生成器模式**：`run()` 改为 `yield` 每步结果，前端逐条渲染
2. **兼容 API 和 Streamlit**：API 层用 SSE（Server-Sent Events），Streamlit 用 `st.write_stream`
3. **向后兼容**：保留同步 `run()` 作为降级方案

### 涉及文件

- `src/agent_core.py` → `run()` 改为生成器模式
- `app_streamlit.py` → 逐条渲染推理步骤
- `src/api_service.py` → `/api/agent/query` 支持 SSE

## OPT-11: 索引状态查询工具（index_status）

### 背景

当前 Agent 不知道自己索引库里有哪家公司的哪年年报，用户问"有没有宁德时代的"时，Agent 会盲目检索然后返回空结果。注册索引状态查询工具后，Agent 可以先查"自己有什么"，再决定怎么检索。

### 设计要点

1. **读取 company_registry.json**：返回公司名列表、数据年份范围、文档数量
2. **轻量实现**：纯本地读取，不涉及 API 调用
3. **Agent 可主动调用**：LLM 发现用户提到未知公司时，先调 index_status 确认是否有数据，有则检索，无则明确告知

### 工具接口

```python
class IndexStatusTool(BaseTool):
    name = "index_status"
    description = "查询当前索引库中有哪些公司、哪些年份的数据可用"
    parameters = {
        "type": "object",
        "properties": {
            "company_name": {
                "type": "string",
                "description": "可选，指定公司名查询详情。不填则列出所有公司"
            }
        }
    }
```

### 涉及文件

- `src/tools/index_status_tool.py` → 新增工具类
- `src/ingestion.py` → company_registry.json 结构保持不变

## OPT-12: 报告生成器（report_writer）

### 背景

当前 Agent 用 Final Answer 输出，格式自由、无结构约束。对于"帮我写一份中芯国际的营收分析"这类需求，注册报告生成器后 Agent 可以把检索+计算+对比的结果组装为固定格式的分析简报。

### 设计要点

1. **结构化模板**：摘要 → 财务概况 → 趋势分析 → 风险提示，每段有固定 Prompt 约束
2. **数据驱动**：接收 retrieve/calculator 的结果作为输入，不自己调检索
3. **引用标注**：每段数据附带来源文件和页码
4. **可选导出**：与 OPT-07 答案导出联动

### 工具接口

```python
class ReportWriterTool(BaseTool):
    name = "report_writer"
    description = "将分析结果整理为结构化的财务分析简报"
    parameters = {
        "type": "object",
        "properties": {
            "company": {"type": "string", "description": "公司名称"},
            "sections": {
                "type": "array",
                "items": {"type": "string"},
                "description": "报告章节，如 ['营收', '利润', '现金流']"
            },
            "year": {"type": "string", "description": "分析年份"},
            "data_points": {
                "type": "array",
                "description": "检索和计算得到的数据点列表"
            }
        },
        "required": ["company", "data_points"]
    }
```

### 涉及文件

- `src/tools/report_writer_tool.py` → 新增工具类（主要是 Prompt 模板工程）

## OPT-02: PDF 解析器可插拔

### 背景

MinerU（VLM 模型）适合表格密集、排版复杂的年报/研报，但对纯文字类文档（合同、法律文书）属于算力过度。需要支持按文档特征切换解析器。

### 设计要点

1. **统一接口**：定义 `BasePDFParser` 抽象类，`parse(pdf_path) -> markdown`
2. **可选实现**：MinerUParser / PyMuPDFParser / pdfplumberParser
3. **按文件自动路由**：首页检测 → 含大量表格 → MinerU；纯文字 → PyMuPDF
4. **`language` 参数外置**：当前 `language="ch"` 硬编码，改为从配置文件读取

### 涉及文件

- `src/pdf_mineru.py` → 重构为 `src/pdf_parsers/` 包
- `config/agent_config.json` → 新增 `pdf_parser` 配置节

## OPT-03: 领域配置外置化

### 背景

当前以下内容硬编码在 Python 代码中，换领域时需改源码：

| 硬编码内容 | 所在文件 |
|-----------|----------|
| 意图分类 Prompt（financial_data 等 6 类） | query_processor.py |
| 已知公司名、财务指标关键词、对比/趋势关键词 | planner.py |
| 公司别名映射 COMPANY_ABBREV_MAP | retrieval.py |
| BM25 同义扩展、jieba 用户词典、单位换算规则 | retrieval.py, config/* |

### 设计要点

1. **意图分类体系 → YAML/JSON 配置**：领域名 + 分类标签 + Prompt 模板
2. **实体识别 → 配置**：公司名列表、别名词典、关键词映射
3. **BM25 + jieba 词典 → 纯配置**：词典文件路径从配置读取，而非硬编码

### 实现路径

```
config/domain_config.yaml  ← 领域配置文件（统一入口）
src/domain_loader.py       ← 领域配置加载器
```

## OPT-06: Token 用量与成本看板

### 背景

`agent_core.py` 每次 LLM 调用已记录 input_tokens/output_tokens，Embedding 和 Rerank API 也有用量日志，但只打印不汇总。用户和开发者都不知道一次查询实际花了多少。

### 设计要点

1. **UsageTracker 类**：按 conversation_id 聚合所有 API 调用的 token 用量
2. **成本换算**：按 DashScope 各模型定价换算为实际金额
3. **展示位置**：Streamlit 侧边栏 或 查询结果末尾显示"本次消耗 XX tokens，约 ¥X.XX"

### 涉及文件

- `src/agent_core.py` → 用量记录接入 UsageTracker
- `app_streamlit.py` → 侧边栏/结果区展示

## OPT-08: 检索结果缓存

### 背景

多步推理中同一家公司同一个指标可能被检索多次（比如先查营收、再算增长率时又查一次营收），每次都走一遍 Embedding + Rerank，浪费 API 额度和时间。

### 设计要点

1. **会话级 LRU 缓存**：key = `(query, company_name, top_n)`，命中直接返回 ToolResult
2. **缓存位置**：放在 `RetrieveTool` 内部，Agent 无感知
3. **容量上限**：默认 50 条，防止内存膨胀

### 涉及文件

- `src/tools/retrieve_tool.py` → 增加 LRU 缓存
- `src/retrieval.py` → 无需改动

## OPT-13: 异常数据检测器（anomaly_scanner）

### 背景

年报中某些指标突然大幅波动（如研发费用翻倍、毛利率骤降），人工逐页阅读容易遗漏。注册异常检测工具后，Agent 可以逐指标比对年度变化率，自动标记偏离超过阈值的条目。

### 设计要点

1. **变化率阈值**：默认标记同比变化超过 30% 的指标
2. **多年度比对**：内部调 retrieve_tool 获取多年数据
3. **输出格式**：异常指标列表 + 变化幅度 + 可能原因提示（如"研发费用增长 80%，可能与新产品线投入有关"）

### 工具接口

```python
class AnomalyScannerTool(BaseTool):
    name = "anomaly_scanner"
    description = "扫描公司财务数据中的异常波动，标记同比变化率超过阈值的指标"
    parameters = {
        "type": "object",
        "properties": {
            "company": {"type": "string", "description": "公司名称"},
            "year": {"type": "string", "description": "目标年份"},
            "threshold": {"type": "number", "description": "异常阈值(百分比)，默认 30"}
        },
        "required": ["company", "year"]
    }
```

### 涉及文件

- `src/tools/anomaly_scanner_tool.py` → 新增工具类，内部复用 RetrieveTool

## OPT-14: 财务健康评分（health_score）

### 背景

投资分析中常用杜邦分析、Z-score、Altman 等模型给公司打分。注册评分工具后，Agent 可以从盈利能力、偿债能力、运营效率、成长性四个维度给出综合评分，满足投资者快速判断的需求。

### 设计要点

1. **四维评分**：盈利能力（ROE、净利率）、偿债能力（资产负债率、流动比率）、运营效率（资产周转率）、成长性（营收增长率、净利润增长率）
2. **数据来源**：内部调 retrieve_tool 获取所需财务指标
3. **评分输出**：百分制 + 各维度明细 + 行业参考区间

### 工具接口

```python
class HealthScoreTool(BaseTool):
    name = "health_score"
    description = "基于盈利能力、偿债能力、运营效率、成长性四维度给出财务健康评分"
    parameters = {
        "type": "object",
        "properties": {
            "company": {"type": "string", "description": "公司名称"},
            "year": {"type": "string", "description": "评分年份"}
        },
        "required": ["company"]
    }
```

### 涉及文件

- `src/tools/health_score_tool.py` → 新增工具类，内部复用 RetrieveTool + CalculatorTool

## OPT-15: 图表存储时效性与容量限制

### 背景

`chart_tool.py` 将 PNG 图表写入 `data/charts/` 目录，当前无任何清理机制，文件会随使用无限堆积。长期运行后磁盘占用持续增长，且旧图表文件路径可能仍被记忆引用但文件已无关紧要。

### 设计要点

1. **时效性清理**：图表生成超过 N 天后自动删除（如 7 天），`ChartTool.__init__` 中增加过期文件扫描
2. **容量上限**：目录内文件数超过上限（如 50 张）时，按修改时间淘汰最旧的
3. **初始化自检**：`ChartTool` 实例化时执行一次清理，而非依赖外部定时任务

### 涉及文件

- `src/tools/chart_tool.py` → `__init__` 增加清理逻辑 + 新增 `_cleanup_old_charts()` 方法

## OPT-04: api_service 读取 agent_config.json 中的 memory 配置

### 背景

`config/agent_config.json` 已配置 memory 参数：

```json
"memory": {
    "working_memory_limit": 10,
    "episodic_memory_turns": 5,
    "enable_long_term": true
```

### 修复方案

`_load_agent_config()` 增加 memory 段的解析，传入 `AgentMemory()` 构造函数。

### 涉及文件

- `src/api_service.py` → `_load_agent_config()` 扩展

## OPT-09: 多格式数据源接入

### 背景

当前只支持 PDF 年报。但企业数据可能散落在 Excel 财务报表、Word 研报、CSV 数据导出中。

### 设计要点

1. **统一入口**：`ingestion.py` 增加 `--format` 参数（pdf / xlsx / docx / csv）
2. **格式适配器**：Excel → pandas 读表格转 Markdown 表格；Word → python-docx 提取文字
3. **与现有流程对接**：所有格式最终都转 Markdown → text_splitter → FAISS 建索引

### 涉及文件

- `src/ingestion.py` → 增加格式分支
- `src/pdf_mineru.py` → 可能需要重构为多格式入口

## OPT-10: 用户反馈闭环

### 背景

当前系统没有用户反馈机制。收集"有用/有问题"标注可以为后续模型微调、检索策略优化提供真实数据。

### 设计要点

1. **反馈按钮**：每个答案下方加"有帮助""有误"两个按钮
2. **数据存储**：反馈 + conversation_id + query + answer 存入 JSON 日志
3. **匿名化**：不收集用户身份信息，仅记录内容和反馈

### 涉及文件

- `app_streamlit.py` → 反馈按钮 + 日志写入
- `src/api_service.py` → 反馈 API 端点（可选）
