# 规格：OpenSpec 生命周期收口与 CI 质量门禁

## 要求：已完成变更归档

已完成且无实际阻塞项的 OpenSpec 变更必须从活动目录归档，且文件内容不得丢失。

### 场景：审核完成变更

- **当** 审核活动变更的任务清单和 TDD 状态
- **则** 仅任务完成、验证记录齐全且无未解决文件的变更可以归档

### 场景：提示词备份收口

- **当** 审核 `prompt-injection-guard` 的 `.py.bak` 清理项
- **则** 仅在确认预期备份文件不存在或获得删除确认后，才可以关闭该项

### 场景：归档后活动目录

- **当** 完成归档
- **则** `openspec/changes/` 根目录只保留真实未完成变更，已归档变更可在 `archive/` 中完整访问

## 要求：基础质量门禁

GitHub Actions 必须在不使用真实服务密钥的条件下验证后端和前端。

### 场景：后端质量任务

- **当** 对 main 推送或创建目标为 main 的拉取请求
- **则** CI 使用 Python 3.11 安装锁定依赖、编译 `src` 并运行白名单 pytest 测试
- **且** 不发起 DashScope、LangSmith 或本机 HTTP 请求

### 场景：前端质量任务

- **当** CI 运行前端任务
- **则** CI 使用 Node 20 执行 `npm ci`、Vitest 和生产构建

### 场景：工作流隔离

- **当** 质量门禁失败
- **则** 工作流不会推送镜像、部署服务或读取部署 Secrets

### 场景：锁文件或质量门禁变更

- **当** main 推送修改 `requirements.lock` 或 `quality-gate.yml`
- **则** Docker Build & Push 的路径过滤必须触发质量门禁与相应镜像构建

## 要求：发布门禁前置条件

当项目选择将 Quality Gate 作为镜像发布门禁时，Docker 构建必须只消费已通过 Quality Gate 验证的提交，且 main 必须配置必需状态检查。

### 场景：质量失败

- **当** 某个提交的 Quality Gate 失败
- **则** 该提交不得触发自动 Docker 镜像推送或服务器自动部署

### 场景：质量通过

- **当** main 上的提交通过 Quality Gate
- **则** Docker 构建只使用该已验证提交的 SHA 构建和标记镜像

## 要求：自动部署可验证性

若仓库保留自动部署工作流，部署凭据和目标服务器必须在受控发布中被验证；部署失败不得被误判为服务器已更新。

### 场景：部署工作流失败

- **当** Deploy to Server 工作流失败
- **则** 发布记录必须明确标记服务器状态为未确认，并保留失败原因待排查

### 场景：部署工作流成功

- **当** Deploy to Server 工作流成功
- **则** 服务器必须拉取与已验证提交对应的镜像，并完成服务重启

## 要求：README 项目状态准确

根目录 README 必须陈述与仓库可验证事实一致的项目、依赖和发布状态。

### 场景：同步当前项目概览

- **当** 更新 README 的项目状态、前端技术栈、测试记录或 OpenSpec 结构
- **则** 版本与依赖信息必须来自当前仓库文件，历史统计与本轮验证必须分开说明
- **且** 不得将未通过的远端 CI、未配置的分支保护或失败后的服务器状态表述为成功

## 要求：部署故障隔离与凭据最小化

在自动部署失败且根因未确认时，后续推送不得自动重试部署；恢复自动化前必须完成一次受控验证。

### 场景：隔离失败部署

- **当** 部署工作流失败且无法取得可验证根因
- **则** 后续质量门禁推送前仅保留手动部署触发
- **且** 记录恢复自动触发所需的 C1 至 C4 验收条件

### 场景：服务器拉取私有镜像

- **当** 服务器从 GHCR 拉取私有镜像
- **则** 使用仅具备所需 `read:packages` 权限的 Secret 注入凭据
- **且** 凭据不得写入仓库、终端输出或工作流日志

### 场景：恢复自动部署

- **当** 手动受控部署已确认 SHA 镜像拉取、服务启动和健康检查成功
- **则** 可在用户确认后恢复 `workflow_run` 自动触发
- **且** 在此之前不得把手动隔离状态视为部署功能已完成

### 场景：手动受控部署的镜像选择

- **当** 通过 `workflow_dispatch` 执行受控部署
- **则** 操作者必须显式提供非空且格式正确的已验证 `image_sha`
- **且** 后端和前端必须拉取该同一 SHA 标签，不能回退为 `latest` 或默认分支当前 SHA

### 场景：恢复后的自动部署镜像选择

- **当** 恢复 `workflow_run` 自动触发
- **则** 工作流必须使用触发 Docker Build & Push 的 `workflow_run.head_sha` 作为两个镜像的标签
