# 多模态与复用方案三轮核查记录

## 第一轮：函数复用、最小变更与重复建设

### 核查问题

- 每项新增能力是否先定位现有文件、类或函数。
- 是否把现有 MinerU VLM、表格文本、索引、事实、证据和前端组件误判为不存在。
- 同一规则是否出现多个所有者。

### 发现

1. 初稿只列出 `VerifyTool._extract_numbers/_scale_to_unit`，进一步核查发现 `Reflector` 也有 `_extract_numbers_from_text/_scale_to_unit`，如果只迁移前者仍会保留第三套视觉换算风险。
2. 初稿覆盖了检索器，却漏列 `src/ingestion.py::build_bm25_index/build_faiss_index/build_company_index`；这会让实施者误建“视觉向量库”。
3. 视觉模型配置若由新模块独立读环境变量，会绕过 `_load_agent_config()` 与现有模型配置治理。
4. 视觉证据支持判断不能另起一套幻觉评分；现有 Reflector 应消费增强来源，而正式门禁仍由 A 阶段统一评测器负责。
5. 设计文档把模块级 `upload_pdf()` 表述成不存在的 `KnowledgeService.upload_pdf()` 类方法，符号名称不准确。

### 已修正

- 将 VerifyTool 和 Reflector 的数字/单位逻辑共同纳入唯一归一器，两个旧类保留兼容方法。
- 把 ingestion 索引构建函数、RetrieveTool、Reflector 和 `_load_agent_config()` 加入函数级复用矩阵。
- 明确视觉结构摘要进入原 FAISS/BM25 与 metadata，不创建第二套向量库。
- 修正知识库上传符号表述，并在任务中加入相应复用约束。

### 第一轮结论

经修正，方案已有函数级而非模块级的复用边界。现有稳定入口默认保留，新建能力集中在制品清单、页图、类型化视觉调用和结构化视觉解析四类真实空缺中。

## 第二轮：端到端技术链路与数据正确性

### 核查问题

- PDF、MinerU、页图、结构化事实、索引、API 与前端能否形成可追溯闭环。
- 局部失败是否会被目录文件、零向量或旧索引掩盖。
- 文件系统与索引的生命周期承诺是否技术上成立。

### 发现

1. `build_faiss_index()` 当前在 embedding 批次失败时补零向量；如果视觉摘要直接复用默认路径，manifest 可能误判索引成功。
2. 初稿给 SourceInfo 增加 `page_image_url`，但未定义安全读取端点；直接挂载制品目录或返回本地路径会产生路径泄露和越权读取风险。
3. 初稿使用“事务性清理”表述，但原 PDF、派生文件、事实库和 FAISS/BM25 不可能参加同一 ACID 事务，这一承诺不可实现。
4. manifest 缺少 schema 版本、持久化原子性和恢复状态；仅检查文件是否存在会把半成品当成功。

### 已修正

- 设计视觉索引 strict 模式：保持旧文本默认行为，视觉 embedding 失败则停止、标记 incomplete，禁止零向量进入可用索引。
- 新增受认证的 artifact ID 读取端点要求，服务端从 manifest 解引用路径；禁止公开挂载视觉目录和接受客户端文件路径。
- 将删除改为 `deleting → 幂等清理 → deleted`，先停止检索，失败时保留可恢复状态，不再伪称跨存储原子事务。
- 为 manifest 增加 schema 版本、明确状态机和原子写入，并增加相应任务与 RED 测试。

### 第二轮结论

经修正，主链的成功状态由 manifest 与严格门禁共同决定；缺页、模型失败、索引失败、删除中断和越权读取均有显式结果，不再依赖隐藏回退。

## 第三轮：验收、成本、安全与求职价值

### 核查问题

- 指标是否可计算、不可被平均分或样本拆分操纵。
- 多模态成本与失败是否能被量化，而不是只展示最佳案例。
- 安全、可访问性和求职演示能否证明工程判断而非模型包装。

### 发现

1. 40 例专集没有开发/留出边界，同一表格或裁剪变体可能同时用于调规则和最终验收，导致指标泄漏。
2. 只有总体低置信拦截率仍可能允许关键财务数字误入 verified；金融高风险错误不能被平均值抵消。
3. 原方案描述了按需路由和缓存，但验收没有要求报告视觉调用比例、缓存、失败率、P95 和价格版本，无法证明成本设计有效。
4. 求职演示只要求成功的表格/图表定位，容易形成“挑最好案例”的演示偏差；缺少显式失败与拒绝结论案例。
5. 页面截图与区域高亮若没有键盘操作和结构化文本等价内容，会降低可访问性，也削弱“企业级交付”主张。
6. 40 例只能证明首版工程闭环，不能支撑跨行业生产泛化宣传。

### 已修正

- 多模态专集按文档/公司拆分，冻结留出集至少 25%，并增加同源裁剪泄漏检查。
- 新增“高风险视觉误入库数为 0”的硬门禁和无证据视觉声明指标。
- 增加视觉路由、缓存、调用、失败、P95 和价格版本报告；成本阈值在真实基线后批准，不凭空编造金额。
- 求职验收同时展示成功定位与拒绝结论失败案例，并明确 40 例不等于生产泛化证明。
- 增加页图高亮键盘操作、替代文本及表格/图表文本等价说明的任务和 RED 测试。

### 第三轮结论

经修正，验收既测准确率，也测高风险失败、数据泄漏、成本、安全和可访问性；求职展示能体现复用、边界设计和失败处理能力，而不只是接入一个视觉模型。

## 总结论

三轮核查共发现并修正 15 项实质问题。当前方案已满足：函数级复用边界明确；多模态是 A→B→C0→M→C1→D→E 中的必选阶段；规格、任务、全红 TDD 和验收指标闭环；缺页、定位不明、模型/索引失败和删除中断均显式处理；成本与求职展示不依赖夸大宣传。后续开发逻辑的追加核查见 `development-logic-two-pass-review.md`；尚未授权修改业务代码。
