# 面向后续开发的两轮追加核查

## 第一轮：实施路径、迁移与兼容

### 核查重点

- 后续开发能否始终保持可运行主线，而不是完成整个大阶段后才集成。
- 新数据库、索引和配置能否安全升级、激活和回滚。
- 旧 API、多个 Retriever 入口和 Windows 文件语义是否被真实覆盖。

### 发现与修正

1. 现有 `ingestion.py --rebuild` 会先删除旧公司索引，`save_registry()` 也直接覆盖文件；原计划若在此基础上扩展，构建中断会让当前服务失去可用索引。已改为不可变 generation 与 staging 校验；后续独立审查进一步收紧为 PublicationSet 原子发布和整组回滚。
2. `RAGGenerator`、RetrieveTool、CompareTool 各自缓存 HybridRetriever；只替换磁盘文件或刷新一个入口会造成同一时刻不同 API 读取不同索引。已增加统一 Resolver；后续独立审查进一步要求请求级固定 publication，使索引、文档、制品和事实使用同一快照。
3. B 的事实存储、M 的 manifest、C 的任务库和 D 的审计若分别实现，会出现迁移器、连接策略和数据真值重复。已统一为分仓储、单版本化 SQLite 的 V7MetadataStore。
4. 原计划缺少数据库迁移失败、未知高版本和启动前备份规则。已增加幂等迁移、事务回滚、备份和未知高版本拒绝写入。
5. 原计划按阶段列任务，但缺少可运行纵向切片。已要求 B 先完成单指标旧 API 试点，M 先完成单 PDF/表格/视觉区域端到端试点，再扩展样本。
6. `_load_agent_config()` 对读取错误存在历史默认回退；若 v7 新能力复用该语义，错误配置可能意外启用错误模型。已规定 v7 独立严格 schema、默认关闭功能开关，开启但无效时 fail closed。
7. Windows 下 FAISS/BM25 文件可能仍被进程持有，不能在激活时覆盖或立即删除。已改为不可变目录和活动引用归零后延迟回收。

### 第一轮结论

修正后，每个阶段都有可单独验证的纵向试点；数据库和索引均支持失败不破坏当前版本、成功后原子激活、必要时快速回滚。下一轮继续核查任务状态、并发和跨模块竞态。

## 第二轮：状态机、并发、幂等与逻辑闭环

### 核查重点

- M 与 C 的阶段依赖是否会迫使开发者先写临时任务系统。
- 超时、取消、重试、并行事件和控制命令是否有明确线性化语义。
- 上传覆盖、索引激活、查询与删除是否可能引用不同文档版本。
- 新持久事件流是否复制现有免鉴权 SSE 风险。

### 发现与修正

1. M 的 PDF/VLM/索引构建本身是长任务，但原顺序把全部 C 放在 M 后，M 必然先临时实现状态、重试和恢复。已调整为 `A→B→C0→M→C1→D→E`：C0 提供通用执行基础，C1 才做研究任务产品化。
2. 当前线程池 timeout 只停止等待，不能终止 Python 线程或远端模型调用；晚到 Worker 仍可能写 SharedMemory。已增加 lease、attempt token、revision 和提交守卫，超时/取消后的结果只能 discarded。
3. 暂停、恢复、取消可能由多个请求并发提交，原计划没有乐观并发控制。已增加 `command_id + expected_revision + CAS`，重复命令幂等、过期 revision 冲突。
4. 并行 Worker 直接向 queue 写事件只能保证队列线程安全，不能提供持久事件号和状态原子性。已规定单一持久化写入器在数据库事务内分配 event ID。
5. 原幂等键只含工具输入与版本，模型、提示词、事实/制品和索引代际变化后可能错误复用旧结果。已把全部依赖版本纳入键。
6. 当前同名 PDF 会直接覆盖，派生事实和索引可能仍引用旧内容。已拆分 logical_document_id/document_version_id，同 hash 幂等，不同 hash 先构建新版本再激活。
7. 删除、查询和索引切换缺少线性化点。已规定 deleting 后新查询排除文档版本、在途请求固定快照、删除完成后 artifact 与新索引不可见。
8. 当前 `/api/agent/stream` 因 EventSource 限制免鉴权；持久任务事件若照搬会暴露任务状态。已要求新任务流使用可带 Authorization 的 fetch streaming，不加入免鉴权前缀，也不在 URL 传长期 Key。
9. 审批仅绑定工具参数仍可能在事实、计划或索引改变后被重复使用。已要求审批绑定 task revision、计划、事实/制品版本和 index generation，并与关键状态、审计同事务提交。
10. 事件被清理后，旧 Last-Event-ID 无法完整补发。已增加保留窗口和“先获取任务快照再重连”的显式响应。
11. 原先设想的单一任务开关无法区分 M 依赖的 C0 内核与 C1 研究任务产品，可能出现多模态开启但执行基础关闭。已拆为四个默认关闭的功能开关，并显式校验依赖，不自动连带启用。

### 第二轮结论

修正后，长任务基础只实现一次并先由多模态入库验证；并发控制、超时晚到结果、文档版本、索引代际、删除竞态、审批失效和事件鉴权均有明确状态与 RED 测试。

## 总结论

两轮共发现并修正 18 项面向开发的结构与逻辑问题。当前方案不再依赖原地索引覆盖、隐式配置回退、临时多模态任务状态或“线程超时等于取消”等错误前提。规划可以进入批准门禁；尚未修改业务代码。
